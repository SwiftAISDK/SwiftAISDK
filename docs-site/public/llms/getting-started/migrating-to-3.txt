# Migrate to 3.0

Source URL: https://swiftaisdk.github.io/SwiftAISDK/getting-started/migrating-to-3/

SwiftAISDK 3.0 makes the existing Swift-native port independently installable.
The optional `SwiftAISDK` product keeps the complete provider, MCP and UI surface.
Smaller applications can select core and just the adapters they use. Swift 6.3,
macOS 12 and iOS 15 remain the declared minimums. Swift versions do not match npm
version numbers; each release records its own upstream baselines and known gaps.

## Keep the complete API

Change the root dependency to:

```swift
.package(url: "https://github.com/SwiftAISDK/SwiftAISDK.git", from: "3.0.0")
```

Keep `.product(name: "SwiftAISDK", package: "SwiftAISDK")` and `import SwiftAISDK`.
The compatibility product retains the existing `AI` facade, `AIProviders`
factories with `settings:`, provider aliases, string model resolution, scoped
default providers and implicit Gateway behavior. Module-qualified legacy names
such as `SwiftAISDK.TextGenerationResult` remain available through the facade.

All implementations now live in their owning packages. The umbrella uses
compatible version ranges; it does not pin an application's complete graph.
Commit your application's `Package.resolved` after validating an upgrade.

## Select core and one provider

For an OpenAI application:

```swift
dependencies: [
    .package(url: "https://github.com/SwiftAISDK/swift-ai-core.git", from: "1.1.0"),
    .package(url: "https://github.com/SwiftAISDK/swift-ai-openai.git", from: "1.0.0"),
],
targets: [
    .target(name: "YourApp", dependencies: [
        .product(name: "SwiftAI", package: "swift-ai-core"),
        .product(name: "SwiftAIOpenAI", package: "swift-ai-openai"),
    ]),
]
```

```swift
import SwiftAI
import SwiftAIOpenAI

let provider = try AIProviders.openAI(
    configuration: OpenAIProviderSettings(apiKey: "your-api-key")
)
let result = try await AI.generateText(
    model: provider.languageModel("gpt-4.1"),
    request: .init(messages: [.user("Hello")])
)
```

Native adapter factories use typed `configuration:` parameters. The compatibility
product retains its existing `settings:` spelling. OpenAI shares wire code with
`swift-ai-openai-compatible`; it does not bring in unrelated providers, MCP or UI.
Some adapters have intentional dependencies on another adapter: Azure on OpenAI,
or Vertex on Google and Anthropic. The catalog and exported manifests show the
actual closure; independent installation does not mean every adapter has zero
adapter dependencies.

Core contains `SwiftAI`, `SwiftAIProvider`, `SwiftAITransport` and
`SwiftAIProviderUtilities`. These four modules initially share one Swift version.
Core works with a consumer-defined model and has no concrete providers or implicit
Gateway. Pass a model explicitly, or construct `createProviderRegistry` with the
providers your app chooses. `AICustomProvider` model-ID aliases require an explicit
resolver when using the native core API.

## Choose independent provider versions

An application can pin OpenAI at `exact: "1.0.0"` and move Anthropic from
`exact: "1.0.0"` to `exact: "1.1.0"`. Their common core requirements must intersect.
Reusable libraries should normally declare compatible ranges, reserving an exact
requirement for an intentional consumer constraint.

SwiftPM selects one version of each package identity. Incompatible core major
requirements fail resolution; separate repositories do not permit two incompatible
copies of the same Swift module in one dependency graph. A provider-only patch
does not require releases of unchanged providers or core. Changes to common
contracts select downstream verification without forcing downstream releases.

## MCP, UI and mixed imports

Select `SwiftAIMCP` from `swift-ai-mcp` for MCP clients and their tool bridge.
Select `SwiftAIUI` from `swift-ai-ui` for native chat state. Both are optional;
the UI package is a Swift adaptation, not React rendering. Provider-specific
platform availability and existing gaps are preserved.

The 3.0 umbrella and direct modular imports share nominal core types. If importing
both facade modules, qualify overlapping facade names, for example `SwiftAI.AI`
or `SwiftAISDK.AI`, and `SwiftAIOpenAI.AIProviders` or `SwiftAISDK.AIProviders`.
Ordinary applications can choose one facade spelling for clarity.

The existing 2.x tags retain their original monolithic types. Do not mix a 2.x
model/request value with modular 1.x APIs. Move the umbrella to 3.0 before sharing
values with a direct provider package. Moving types between modules is a source
migration, not a binary compatibility guarantee: rebuild clients and dependent
frameworks. No existing 2.x tag is rewritten. The 2.x line remains available for
pinned applications; ongoing feature ports use modular releases, with any 2.x
backport evaluated separately.

## Contribute and synchronize upstream

Edit the canonical `SwiftAISDK/SwiftAISDK` repository. Distribution repositories
are generated, independently versioned outputs. Their provenance maps each
release back to its canonical commit, source/test paths and reviewed npm archives.

```sh
node Scripts/sdk.mjs dev build
node Scripts/sdk.mjs dev test --no-parallel --filter yourFocusedTest
node Scripts/test-packages.mjs
node Scripts/sdk.mjs dev examples build
```

The root `Package.swift` always uses public Git dependencies. The `dev` command
generates an ignored workspace under `.build/development/SwiftAISDK`, links the
canonical sources/tests, and derives local dependencies from the same catalog.
It does not rewrite the public manifest or add environment-dependent package
resolution. Run `swift test` at the root when intentionally testing the public
dependency graph; run the wrapper to include every package's own tests.

For a selected upstream update, `sdk.mjs upstream prepare` verifies archive
integrity, resolves immutable test revisions, records changed files/declarations,
maps Swift owners and selects downstream checks. A missing release test ref is
explicitly recorded as a gap. Preparation never advances reviewed baselines.
Translate behavior and tests, record dispositions, then update the structured
ledger and release entry. See [the porting guide](https://github.com/SwiftAISDK/SwiftAISDK/blob/main/Docs/AgentPortingGuide.md) and
[release workflow](https://github.com/SwiftAISDK/SwiftAISDK/blob/main/Releases/README.md).

Adding a selected provider starts with one `sdk.mjs package add` registration.
Manifests, package indexes, CI selection and export inputs are generated. An empty
or unreviewed scaffold cannot be released. This migration does not automatically
select newly discovered upstream packages or claim complete upstream parity.
